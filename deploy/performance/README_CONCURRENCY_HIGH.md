## 一条命令执行

在解压后的客户端目录执行：

```bash

```

| --- | --- | --- | --- |
| 第一档 | mac_c68_20261019_c6 | 6 | 6 个 |

第二档只会在第一档验收通过、归档同步成功、活动 RPC/执行中/排队回落后开始。任何异常均停止，不继续第二档。服务端登记防止重复执行、跳档或失败后继续发任务；本轮最多 14 个新增真实任务，全部完成后停止，不自动升至更高档位。

每次启动先检查 Mac 到网站的 DNS/TLS/HTTP 连通性和监控隧道，再登记批次，降低网络问题提前消耗任务额度的概率。启动后的断线不保证后端任务取消，禁止自行重复普通启动命令。

## 自动验收

每个任务必须发布、报告保存可读、有非空指标及章节、用量可见，且 OCR、VLM、报告草稿与保存阶段成功；所有任务与报告 ID 应不同，报告版本为 1。逐任务读取服务端日志，不用整批出现过一次成功阶段代替。

服务端根据每个任务 vision_observe 的结束时间和耗时还原区间，要求本档全部 6 个或 8 个任务确实同时重叠。只创建了多项任务但实际串行执行，不通过本轮并发验收。

单任务超时 300 秒；每档报告可读中位数暂以不超过原单任务 21.558 秒的 1.5 倍（约 32.34 秒）作为升档初筛目标。超过时停止并调查，不直接宣布容量上限。资源保护、模型限流/失败、未知在途状态、归档缺失也会阻止继续升档。

可见 Token 软上限分别为并发 6 档 180,000、并发 8 档 240,000，整轮 420,000。按已有每任务约 1.1–2.2 万 Token 粗估，14 个任务约 15.4–30.8 万 Token；实际随重排缓存和模型输出变化。软上限不是账单硬上限，在途用量可能突破；本轮会真实调用模型并产生费用。

## 输出与异常恢复

每档结果位于 results/<run_id>/client 和 server-archive。concurrency-validation.json 包含 healthy_concurrency_passed、errors、server_vision_overlap_seconds、逐任务报告耗时和 Token；两端结果自动同步，无需回传 client.env。

若第一档失败或未知状态，停止，不运行第二档。若仅需在任务回落后补充导出，不创建新任务：

```bash
# 第一档补充导出
.venv/bin/python client/run_high_steps.py --batch 1 --finalize

# 第二档补充导出
.venv/bin/python client/run_high_steps.py --batch 2 --finalize
```

--batch 1 表示并发 6，--batch 2 表示并发 8。失败不会重置已登记的任务额度。若第一档已通过，但 Mac 在开始第二档前退出，可用下面的命令只继续第二档；服务器会核对上一档是否通过：

```bash
.venv/bin/python client/run_high_steps.py --batch 2
```

保持 Mac 唤醒和网络稳定。不要并行运行多份脚本，不要清空线上缓存或修改应用配置，否则对比条件会改变。

## 结论范围

这两组分别只有 6 和 8 个任务，能够证明短时并发链路是否可行，不能证明稳定 P95、持续吞吐、最大容量、长稳或故障恢复。原 ready_for_load=false 保留未完成的文件归属/部署/权限与隔离门禁；本轮由独立的用户授权登记允许线上受控分档模式，不伪造正式容量就绪结果。原 closed/arrival 模式仍禁止对生产域名直接运行。
